# Дизайн: детекторы несоответствий v1 (правила + генератор)

Дата: 2026-10-09. Статус: на проверку.

## 1. Цель и контекст

Второй подпроект серии «новые методы поиска по данным». Цель — ловить в ПЗ несоответствия, которые правила
v0 (`src/crossvalidation/rules.py`) пропускают. Пропуски на реальной ОПЗ, все с причиной «нет правила»
в `annotations/real/misses/real_opz_zhbi2.json`:

| Находка | Тип | Суть |
|---|---|---|
| R3 | `TEP_CALCULATION_METHOD` | строительный объём = площадь застройки × высота помещения в чистоте |
| R6 | `VALUE_CROSS_SECTION_MISMATCH` | абсолютная отметка 0.000 на ~175 м выше рельефа площадки |
| R8 | `COPY_PASTE_LABEL` | таблица раздела «Здание цеха» подписана «Здание офиса» |
| R9 | `PARAMETER_CONTRADICTION` | отмостка: бетонная 1000 мм против асфальтобетонной 1,5 м |

**Область:** ПЗ с текстовым слоем (PDF), RU и KZ, только правила, без LLM.
**Вне области:** R7 (`STATEMENT_CONTRADICTION`, нужен смысловой анализ), R10 (`IRRELEVANT_REFERENCE`, знания
о нормативах) — следующий подпроект; сверка ПЗ с АР/КР/сметой на реальных пакетах.

**Ограничения:**
- реальные документы никуда не отправляются;
- метрика — синтетика; реальная ОПЗ — проверка работоспособности: правила пишутся с оглядкой на неё,
  и это указывается рядом с цифрами;
- замороженный протокол экспериментов (`protocol-v1`) не меняется (раздел 4).

## 2. Детекторы (`src/crossvalidation/rules_v1.py`)

Модуль запускается после v0 на тех же `pages`/`PageText`/`ObjectIndex` и возвращает `Finding` той же схемы
(`src/evaluation/schema.py`), с объектом, ссылками «страница + цитата» и уверенностью. Объект значения
определяется как в v0 (`crossvalidation.objects.resolve`): упоминание в предложении или ближайший заголовок
здания; не определён — значение не сравнивается.

### 2.1. Метод расчёта объёма (`TEP_CALCULATION_METHOD`, поле `construction_volume_m3`, «эксперту»)

Входы по зданию: строительный объём V, площадь застройки S, этажность N (ТЭП извлекателя ПЗ), высота H
из фраз «высота помещений (в чистоте) … 2,6 м», «высота этажа … 3,3 м» (RU/KZ, словарь параметров, 2.4).
Находка, если выполнено одно из:
- **V ≈ S × H_чист** (допуск 0,5 %) при известной высоте помещений в чистоте — объём посчитан по
  внутренней высоте, а не по наружному обмеру до верха покрытия;
- **V / (S × N) < 2,8 м** — средняя высота этажа по объёму ниже правдоподобной (меньше типовой высоты
  этажа с перекрытием); порог — константа модуля, подбирается на dev.
Ссылки: значение объёма и значение(я), из которых видно расхождение.

### 2.2. Отметка и рельеф (`VALUE_CROSS_SECTION_MISMATCH`, поле `absolute_elevation_m`, «эксперту»)

Входы: абсолютная отметка 0.000 по зданиям («соответствует абсолютной отметке 489,79») и отметки рельефа
площадки («отметки поверхности от 314,75 м до 315,04 м», «абсолютные отметки … изменяются от … до …»).
Находка, если отметка здания вне [min − Δ, max + Δ], Δ = 3 м (константа; планировка редко поднимает
здание выше). Отметки разных зданий между собой не сравниваются.

### 2.3. Подпись таблицы (`COPY_PASTE_LABEL`, поле `object_label`, «точно»)

В таблице внутри раздела здания X (заголовок раздела — объект X по `ObjectIndex`) первая ячейка строки
данных, подпись над таблицей или название в шапке называет другое здание Y документа, и X в таблице не
назван. Сводные таблицы по нескольким объектам (≥ 2 строки с разными зданиями) не проверяются. Ссылки:
ячейка/подпись и заголовок раздела.

### 2.4. Параметры здания (`PARAMETER_CONTRADICTION`, «точно»)

Общий механизм вместо отдельного правила на параметр. Параметры описаны в новом словаре
`src/ner/data/parameter_lexicon.json` (RU/KZ, с источниками, как `tep_lexicon.json`):
- `blind_area` (отмостка): материал (бетон, асфальтобетон, …) и ширина (мм/м → мм);
- `roof` (кровля): тип/материал;
- высоты для 2.1 (`clear_height_m`, `floor_height_m`).

Для параметра словарь задаёт ключевые слова упоминания и извлекатели значений (категория по словарю
синонимов, число с единицей). Каждое упоминание получает объект (`resolve`; фраза в общем разделе без
здания — объект `all`). Находка, если у одного объекта (или у `all` и здания) значения одной составляющей
различаются: разный материал; ширина с разницей > 1 %. Сейсмичность и огнестойкость остаются в v0.

## 3. Генератор: профиль `v4`

`v4` = `v2` + новые части ПЗ и новые типы ошибок. Своя ветка RNG (`{lang}:{seed}:v4`): `v2` и `v3` не
меняются ни в одном байте (тест).

Новые части (RU и KZ, параллельные шаблоны):
- раздел «Инженерно-геологические условия / рельеф»: диапазон отметок площадки;
- по каждому зданию: абсолютная отметка 0.000, высота помещений в чистоте и высота этажа;
- конструктивные решения: отмостка (материал, ширина) и кровля — в разделе здания и в общем разделе
  благоустройства (фундамент — позже, тем же механизмом словаря);
- подпись таблицы показателей здания с его названием.

Внесение ошибок (новый `SYNTHETIC_TYPES_V4_EXTRA`, каждая с вероятностью 0,5, как в v2), с записью в
`ground_truth.json` (`discrepancies[]`, `consistent_checks[]`, ссылки `mention`):
- `TEP_CALCULATION_METHOD`: высота в чистоте одноэтажного здания указана так, что S × H_чист = V (значения
  ТЭП `v2` не меняются); второе условие детектора (средняя высота этажа) генератором не вносится;
- `VALUE_CROSS_SECTION_MISMATCH`: отметка здания вне рельефа (сдвиг 20–200 м), совпадения — внутри ± 1 м;
- `COPY_PASTE_LABEL`: подпись таблицы здания именем другого здания документа;
- `PARAMETER_CONTRADICTION` по `blind_area`/`roof`: разный материал или ширина в разделе здания и в общем разделе.

## 4. Протокол экспериментов

- `analyze_package(paths, detectors="v1")`: `"v0"` — поведение `protocol-v1` (извлечение ТЭП ступенью
  `exact`, правила v0), `"v1"` — все ступени извлечения + правила v0 + `rules_v1`. Сервис (`api/`) — `"v1"`.
- `RulesSystem` (S1) вызывает `detectors="v0"`; новая система `RulesSystemV1` (S2) — `"v1"`.
- Тест: на нескольких финальных seeds (8000–8002, RU/KZ) S1 даёт те же слоты, что код на теге `protocol-v1`
  (эталон сохраняется в `tests/data/s1_protocol_v1_slots.json` один раз, прогоном кода тега).
- E2/E3 не перезапускаются. Если тест покажет, что S1 после работы над извлечением ТЭП уже отличается от
  `protocol-v1`, это исправляется возвратом S1 к эталону, а не пересчётом экспериментов.

## 5. Оценка

`scripts/eval_detectors.py --profile v4 --seeds …`: генерирует наборы, запускает S1 и S2, считает P/R/F1 по
слотам (тип, поле) и отдельно по каждому новому типу (`src/evaluation/match.py`, как E3). Dev-seeds 1–50
для разработки и порогов, test-seeds 9000–9099 — один итоговый прогон.

Регрессия: на `v2` (seeds 8000–8019) S2 не добавляет ложных срабатываний относительно S1. Реальная ОПЗ
(`scripts/evaluate_real.py` с S2): R3, R6, R8, R9 найдены, ложных находок нет, R1, R2, R4, R5 по-прежнему
найдены.

## 6. Ошибки и деградация

- Детектор, которому не хватает входов (нет высоты, нет рельефа, один объект), молча не срабатывает.
- Значение без объекта не сравнивается (как v0).
- Исключение в одном детекторе не роняет проверку: детектор пропускается, предупреждение в `warnings`.

## 7. Тесты

- Юнит-тесты каждого детектора на собранных вручную страницах (как в `tests/test_tep_extraction.py`),
  RU и KZ, включая отрицательные случаи: объём по наружному обмеру; отметка внутри рельефа ± Δ; сводная
  таблица с несколькими зданиями; одинаковая отмостка в двух местах.
- Генератор: `v4` не меняет `v2`/`v3`; внесённые ошибки достижимы (значения есть в PDF по якорям).
- Протокол: S1 совпадает с эталоном `protocol-v1`.
- Регрессия v2 и реальная ОПЗ (пропуск, если файла нет).

## 8. Критерий успеха

- На `v4` test-seeds F1 по каждому из четырёх новых типов ≥ 0,8 на RU и KZ; точность S2 в целом не ниже S1
  на `v2`.
- На реальной ОПЗ S2: ≥ 8 из 10 находок (R1–R6, R8, R9), 0 ложных.
- README: таблица S1 против S2 по типам на `v4` и оговорка про реальную ОПЗ.
